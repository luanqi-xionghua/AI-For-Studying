# 1.2.7

修复「应用放久了界面卡死」的根因。

## 原因

背景动画里「走遍二十面体（凯莱图 A₅）」这个画面，推进循环把**数组长度**当成了步数进度：

```ts
const steps = Math.floor(env.t / 2800)
while (walk.length - 1 < steps) {
  walk.push(...)
  if (walk.length > 40) { walk.splice(0, 20); /* 数组被裁到 21 */ }
}
```

但数组每超过 40 条就被裁剪回 21 条。于是：

- 画面播放约 115 秒、走到第 41 步时，`walk.length - 1` 永远到不了 `steps`，**while 变成同步死循环**，渲染线程被占满；
- 窗口最小化、被隐藏或系统休眠后 rAF 暂停，恢复时 `env.t` 一次跳几分钟到几小时，会把死循环提前触发。

卡死时后端 HTTP 仍正常、Qt 主线程空闲（窗口不报「未响应」），所以看起来像「放久了卡死」，实际是页面 JS 空转。

## 修复

- 新增 `frontend/src/sketch/walk.ts`：把推进逻辑抽成 `advanceWalk(state, targetSteps, next, flip)`；
- 用**独立的绝对步数 `done`** 代替数组长度，不再依赖会被裁剪的数组；
- 时间跳变时只补最近 40 步（`CATCH_UP`），与同文件洛伦兹吸引子、生命游戏已有的跳变保护一致；
- `scenes.ts` 的凯莱图画面改为调用它，绘制逻辑与视觉不变。

## 验证

- 单测：新增 `sketch-walk` 6 项（t=0、正常帧、连续帧与单次推进一致、10 小时跳变、反复大跳变、跳变后继续正常推进）；前端 **618 项**、后端 88 项全绿。
- 旧版对照：给页面 rAF 时间戳注入 +200 秒跳变后，渲染进程 10 秒消耗 **11.73 秒 CPU**、页面 `Runtime.evaluate` 不再返回；修复版同一注入下 10 秒 CPU 约 3.7 秒（正常动画开销）、页面 3ms 响应，越过旧的 41 步死循环点（130 秒）后仍 4ms 响应。
- 用旧算法原样模拟 41 步：循环超过 100000 次仍未退出，确认死循环。

## 说明

- 不涉及模型、API、数据库结构、依赖变化；`library.sqlite3` 的 schema 与 `user_version` 不变。
- 排查了 `scenes.ts` 全部画面与 `networks.ts`：只有凯莱图这一处用数组长度当进度；洛伦兹与生命游戏已有 `target - done` 的跳变封顶，其余循环要么有界、要么已有跳变保护。
